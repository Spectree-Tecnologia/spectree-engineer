# Changelog

Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versioning: [SemVer](https://semver.org/) — `MAJOR` when a project generated by the previous version stops working with the new one (layout, `skills.config.json`, `ARCHITECTURE.md`), `MINOR` for a new agent, skill, rule or step, `PATCH` for a fix with no change in behavior. **Every merge to main is a release**: the PR already bumps `version` and writes its section here, and the merge gets the tag.

## [0.52.0] - 2026-11-24

**A ticket closes on its gate, the whole diff is reviewed once, and the prototype no longer holds what has no screen.** This release removes steps and adds none. Measured on a pilot project's goal on 2026-11-24, from its transcript: the build started 75 minutes in (45 of machine, 30 waiting for the founder), and then took 156 minutes for three tickets and 438 product lines. Half of that was the review, the fix and the re-check of each ticket.

### Changed
- **Nobody reviews a ticket (step 7).** The checkpoint is the ticket's gate, by exit code, and the Engineer writes `Status: verified` from it. The `quality-engineer` and the `security-engineer` read the whole diff once, at the final verification (step 8), which was already mandatory. Measured: 16, 22 and more than 41 minutes per ticket in review, fix and re-check; a 37-line ticket went through three fixes.
- **`goal graph` prints no `trust:` line** and its `--json` has no `trust` key. All 10 tickets of the measured plan were under it, so it chose nothing.
- **Mutants are read once (quality-engineer).** In the first final round only. A surviving mutant is a `nit` marked `hardening` that goes to the hardening goal; it is `weak proof` only when the missing test is the proof of a criterion. Measured: one whole fix round was two surviving mutants.
- **The handoff point is call 90, not 60 (panel), and a ticket is sized for about 60 calls (`to-tickets`).** Two of three tickets were handed off at call 60, one before it had run anything, and the missions that went on to 89 turns cost no more per turn. `to-tickets` now says a ticket has a fixed cost: the fewest tickets that each fit, one per criterion as the usual size.
- **The prototype holds only the criteria that show it (step 2).** While the founder looks, the contract, the plan and the build go on for the criteria that name no artboard. Screen criteria enter by an `added` amendment when the founder approves, with their own plan mission. The stage is still the founder's, with no ceiling on rounds. Measured: 47 minutes of prototype and wait before a backend that did not depend on them.

### Added
- **A receipt for a ticket's gate.** `goal gate <slug> --ticket <n> --since <sha>` that was green keeps a receipt outside the repository. The same command on the same code (nothing outside `.scratch/` changed, same `--since`, same proof) prints the `R` lines and `receipt:` and runs nothing; `--rerun` runs it. A red gate and a dirty tree keep none. The full-stack-developer closes a ticket with the gate, and the Engineer's gate reads that run. Measured: 142 to 181 seconds per run, two to three runs per ticket.

### What is no longer guaranteed
- A defect in an early ticket is found at the final verification, after later tickets were built on it. The final round reads more code and may cost more than it did.
- A surviving mutant no longer blocks a merge.
- A founder's answer on a prototype that changes a rule already in the contract costs an amendment and a new plan for the tickets it touches.
- A goal in flight under 0.51 keeps its tickets' `open`, `Carried:` and `Reproved:` lines, which the graph still reads; the command no longer writes them.

### Not proven
- No goal ran with this text: every gain is an estimate from one goal's transcript (2.5 to 3 hours per goal for the ticket review, about 25 minutes for the receipt). How much longer the final verification gets was not measured.
- The panel cannot see a mission's context size while it runs, so the handoff point is still a count of calls.
- The evals were not run.

## [0.51.0] - 2026-11-24

**The gate cannot hang, and size, env and moved criteria are read the way CI reads them (issues #130, #132, #133 and #134).** This release adds no check or round. Each issue was seen on a pilot project: a gate hung for 16 hours, a goal was split on a size that included the squad's own scripts, a local `.env` turned e2e red, and a contract split under 0.43 had every criterion skipped.

### Fixed
- **`perf.mjs` and `goal gate` (#130).**
  - A backend killed by a signal keeps `exitCode` null. `stopChild` now also checks `signalCode`, so a second stop no longer waits forever on an `exit` that already fired.
  - Each measurement request has a 30-second timeout (status 0), and the readiness probe has 5 seconds.
  - Each gate step has a timeout, 60 minutes by default (`GATE_STEP_MINUTES`). A step that hangs is a red that says it timed out, and its log stays.
  - On Windows, a process the timed-out step started may survive the shell it ran in.
- **`goal size` (#132).** The files listed in `scripts/.squad-tooling.json`, which `tooling-sync` owns, are not product code. They are printed as `squad tooling` on the "not counted" line.
- **Proof env (#133).** `goal prove`, `goal graph --prove` and every `goal gate` step run with CI's env: UTC, and blank for each key of an app's local `.env` that its `.env.example` gives no value (CI copies `.env.example`). A key the shell itself sets is left alone. The blank keys are printed.
- **Moved criteria (#134).**
  - `goal check` refuses a `reworded` or `narrowed` row that changes a criterion after its `moved` row.
  - `goal prove` is red when every criterion is moved or waived. Before, it said "nothing to run" and exited 0.
  - `to-goal` says that only whole rows move. A part kept here becomes a new criterion (`added`).

  - Untracked logs already in a project's `.scratch/` are the project's to delete.

## [0.48.0] - 2026-11-21

**The generated backend writes no credential to its request log, and `check:pr` proves the gitleaks digest (issues #104 and #99).** This release adds no check or round. Both were seen on the pilot project: one e2e log held 42 refresh tokens, and a zeroed digest still said `ok gitleaks`.

### Fixed
- **Request log (#104).** `config-shared-backend` writes the request line by allowlist, in `config/log-redact.ts`: the method, the path cut at the query, the ip and the status.
  - Before, only `authorization` and `cookie` were redacted. The response's `set-cookie` (`refresh_token=`) and a magic link's `?token=` reached every request line, in production too.
  - `log-redact.spec.ts` sends a request through pino-http with a cookie, an authorization header and a query token, and checks the log holds none of them. On the pilot backend it passed with the allowlist and failed without it.
  - An existing project keeps its own files: `apply.js` overwrites only with `--force`.
- **gitleaks pin in `check:pr` (#99).** The scan uses the pinned image whenever Docker answers, so pulling it by digest proves the pin in `ci.yml`. The local binary is used only without Docker, and the output then says the digest is CI's to prove. Before, a local binary of the pinned version ran instead and the digest was never read.

## [0.47.0] - 2026-11-21

**Fixes in six scripts that turned green code red or said the wrong thing (issues #114, #115, #116, #87, #88 and #107).** This release adds no check or round. Each issue was seen on the pilot project.

### Fixed
- **`goal-start --baseline` (#114).**
  - After `npm ci`, it runs `npx prisma generate` in the backend. `npm ci` empties `node_modules/.prisma`, and 15 backend test files then failed on green code.
  - A test step whose worker died while starting (Vitest's fork on Windows, exit 2147483651) is run once more. The record says so and keeps both logs. A test that fails for a reason of its own is red the first time.
- **`db:scratch` (#115):** `db:roles` runs under a Postgres advisory lock. Two runs started together (the quality-engineer and the security-engineer on one ticket) no longer die on `tuple concurrently updated` before any test runs.
- **`goal graph` (#116):** `Reproved:` is read only up to the end of the list of numbers that opens it. Before, the digits of a sha after the list were counted as criteria.
- **`perf.mjs` (#87).**
  - A route the base served within budget, which this change took over budget by less than `regressionRatio`, is no longer worded "over budget on the base, not this change". It is now `OVER, WITHIN RATIO`, with a line that says what happened.
  - The reason a base run died is its first error line, not Node's `Node.js v<version>` banner.
  - Before turning red, it samples the CPU again with the server stopped. A busy machine is exit 3, "not measured", the same as a busy start.
  - Not done: `npm ci --ignore-scripts` + `npm rebuild` in the base worktree. The base's lockfile is main's, which the scanners have already read, and `npm rebuild` runs the same install scripts anyway.
- **`goal check` and `tooling-sync` (#88).**
  - `goal check` with no slug reads a finished contract (`met`, `landed`, `stopped`) as history, so a later checker's errors on it become notes. A contract named by its slug, or one the branch changed, is still checked in full.
  - `tooling-sync --check` lists the open contracts the plugin's `goal check` refuses, with each error. It changes nothing and decides nothing.
  - The assets are versioned and checked out with LF (`.gitattributes`), so a byte comparison with a project's copy holds.
- **Security audit on Windows (#107):** `skills/security/validate-coverage-ledger.cjs` is a Windows entry point for the coverage-ledger validator, like the one the findings validator already had. It reads the file plainly and runs the same preflight and validation, and on other platforms it calls the original CLI. The Engineer's Audit section names it.

## [0.46.0] - 2026-11-21

**A screen criterion is proved against its artboard by computed style, and the contract closes four classes that cost rounds (issues #121, #106, #90, #96, #98 and #97).** This release adds no check or round. Measured on the pilot project: a screen criterion of statement-of-accounts-2 was reproved at five checkpoints in a row, each one on a property its spec had not copied from the artboard. In `e2e-hardening`, one gate's message took three extra final rounds. In `ts7`, a proof was reproved five times because it recognised only the forms it remembered. In `ci-time-20`, a push cancelled a counted run, and `gh run watch` exited 0 on that cancelled run.

### Added
- **`scripts/artboard.mjs` (`compareArtboard`), with `scripts/artboard.d.mts` for TypeScript specs.** A Playwright spec gives it the artboard's `.dc.html`, the root of the frame on both sides and named probes.
  - It compares every element that draws something inside a probe (a text, a painted box, an icon, a `::before` or `::after`) with every computed property, plus its geometry relative to the root and the box of its own text.
  - It skips an exclusion list in which each entry carries its reason, and `exclude` refuses an entry without one.
  - It returns by name whatever the artboard draws outside every probe.
  - Tried against a real artboard: compared with itself it gives no difference, and a changed radius, colour or font is listed.
  - `project-init` installs it and `tooling-sync` keeps it in step.

### Changed
- **`to-goal`:**
  - A screen criterion's proof is a spec that calls `compareArtboard` for each artboard and state of its list. A screenshot is evidence for the founder, never the proof (#121).
  - A gate decides the refusal (the exit code) for every input. The message's content is demanded only for a closed list of cases, and a message outside that list is a `should` (#106).
  - A deferred proof names only commits that are on main, because main is squash-merged (#98).
  - A criterion decided by hand from the PR's own run is written `in ci:` with no `run:`. It stays `pending`, and `check:pr` passes before the PR opens; `goal check` already accepted this (#97).
  - A run's verdict is its jobs' conclusion (`gh run view <id> --attempt 1 --json jobs`), never `gh run watch`'s exit code (#96).
- **full-stack-developer card:** a proof that judges another tool's input reads it with that tool's own parser and fails on any form it cannot judge (#90).
- **platform-engineer card:** a push to an open PR cancels its run in progress. While the goal needs that run, what is recorded about it is committed without a push (#96).
- **Word budget:** the squad was lowered to 20593. The new text was paid for by removing text the panel already enforces (an interpreter reading stdin) and a rule for sessions from before Goal-Driven Development.

## [0.45.0] - 2026-11-21

**Shorter missions and a Playwright proof that runs alone (issues #122, #118, #117 and #120, part 1).** This release adds no check, test or round. Measured on the pilot project's goal statement-of-accounts-2: 11 of 27 full-stack-developer missions hit the 60-call handoff before running their proof, for 45% of that role's tokens, and each continuation explored the codebase again. One mission stalled for about 7 hours on a hung command. Each goal built its own Playwright harness under `.scratch/`, and the contract's `run:` line failed outside that harness. That failure surfaced only at the final gate and cost a round on Fable.

### Added
- **`scripts/pw.mjs` (`npm run pw -- [<spec>...] [--timeout <minutes>]`).** Runs the Playwright specs of a proof alone. The script refuses before it starts anything if a port in the checkout's `.env` already answers. It builds through the turbo cache and gives the run its own database (`db:scratch`). It starts the backend and `next start` and waits for each to answer while checking that its process is still alive. Logs go to `.scratch/pw/<run>/`, exposed as `BACKEND_LOG` and `FRONTEND_LOG`. Every process the run started is killed with its children at the end or at the timeout (default 20 minutes, exit 124). `project-init` and `tooling-sync` install it as the `pw` npm script.

### Changed
- **`to-goal` and `to-tickets`:** a Playwright proof is `run: npm run pw -- <spec...>`, the same line in the contract and the ticket. A harness under `.scratch/` is never the proof, and a screen criterion is decided by a script, not by hand.
- **`to-tickets`:** a screen ticket covers at most one artboard group and names the spec and fixture it extends. When a new component and a new spec with fixtures are both needed, they are two tickets. `Next needs:` is written as each fact is learned, not only at the end.
- **full-stack-developer card:** a continuation after a `handoff` reads `Next needs:` and the last `wip` diff instead of exploring the codebase again. Past call 45, it starts no long command and hands off instead. Playwright specs run through `npm run pw`.
- **Engineer, the mission guard-rails:** every command is bounded. A command that may run past 5 minutes goes in the background with a timeout, and a hung one is killed with its children and reported. **Step 9:** more than three findings of different classes go to two full-stack-developers in sequence, split by class.
- **Word budget:** both budgets were lowered to what is left (command 8836, squad 20618). The new rules were paid for with text that `npm run pw` and the guard-rails made redundant.

## [0.44.0] - 2026-11-19

**Fewer Actions minutes per goal: the Playwright specs a change can reach, a weekly full run instead of a nightly one, no workflow_dispatch to try or time CI, and a runner the founder can move off billed minutes.** Measured on the pilot project's whole Actions history (197 runs, 529 jobs, 2,131 billed minutes from 2026-10-31 to 2026-11-19, when the organization hit its spending limit and CI stopped starting):
- Until 2026-11-11, before one job and no push: 1,519 minutes. A push to main repeated each merged PR (743), and the Security workflow's four jobs of 20 seconds each billed one minute apiece (192). Both are already gone. 2026-11-11 to 11-14: 331, 188 of them CI tuning.
- Since the CI ran by moment (2026-11-14 on): 281 minutes in five days. Of these, 146 (52%) went to the CI-tuning goal timing the runner with `workflow_dispatch`, 69 to the nightly run and 64 to the PR runs of three goals.
- Every ready PR in that window (9 of 9) ran the whole Playwright suite (437-469 tests, 8-10 of its 13-22 minutes), because any non-spec file under `e2e/` counted as the harness. The nightly run then repeated that suite on main's tree, at about 20 minutes a day.
- A typical goal (`statement-of-accounts`, one push) cost 22 minutes at its PR and 20 at the next nightly run, 42 in all.

### Changed
- **`ci.yml`: the Playwright specs a change can reach.** The scope step runs the new `scripts/e2e-scope.mjs`, which picks the smoke, the specs the PR adds or edits, and the specs that import a changed e2e helper (transitively, or by naming it in a string). It runs the whole suite on the config, the lockfile, a non-module file, a deleted or orphan module, or a selection that covers everything. On the pilot project's PR #33 it picks 18 of 58 specs, 37% of the suite's test time. PRs that changed the config (#30, #34) or the lockfile (#32) still run everything.
- **`ci.yml`: weekly, not nightly.** The full run (the whole suite and every route's p95) runs on Monday when something merged in the last 7 days, otherwise only the scanners. It also runs on demand (stage `weekly`) and before a release (`pre-release`, unchanged). The merge gate on a ready PR is unchanged.
- **`ci.yml`: `runs-on: ${{ vars.CI_RUNNER || 'ubuntu-latest' }}`.** The same job and gate can run on a self-hosted runner the founder registers. GitHub does not bill those minutes today; its self-hosted charge announced for 2026-03 was postponed. Without the variable, nothing changes. `setup-node` now runs before the scope step.
- **platform-engineer card and `to-goal`.** The PR's own run is CI's measurement: no `gh workflow run` on a branch to try or time a change, and no contract budgets dispatch runs. `runs-on` stays `vars.CI_RUNNER` or `ubuntu-latest`, and the runner is the founder's (gate 1).
- **CI Postgres on its own host port and an empty volume.** The compose file `config-prisma` writes now maps `${POSTGRES_HOST_PORT:-<project port>}:5432`, so development keeps its port. The CI's Postgres step moves both database URLs in its `.env` to 55433, sets `POSTGRES_HOST_PORT=55433`, and runs `docker compose down -v` before `up`. Both problems showed up on the pilot's first self-hosted run (2026-11-20). WSL2 distros share one network, so CI asked for the port the developer's database already held. A self-hosted runner also keeps volumes between runs, where a hosted one starts empty.
- **Projection for a typical goal on the hosted runner:** a 16-minute PR run (Playwright 10 → 3.7 min), plus a 20-minute weekly run shared by about four goals, comes to about 21 minutes against 42, a 50% cut. With `CI_RUNNER` set, billed minutes go to zero and the gate stays the same. The 80% target needs the runner.
- **Word budget.** Unchanged: the card's new rules paid for themselves with redundant parentheses that left.

## [0.42.0] - 2026-11-16

**A shorter final verification: one round and its re-check, no review of what a checkpoint already reviewed, and a checker's criterion that can close.** The founder wants the pipeline of a feature shorter and no improvement that adds checks, tests or rounds ("Sim, os três"). Measured on the pilot project's `e2e-hardening` goal (12.8 h wall): the three tickets took 2 h 21 in one checkpoint round each, and the final verification took 9 h 05 in four rounds, all on one criterion. Each round was opened by a new quality-engineer who found a new class of bypass in a checker script.

### Changed
- **Step 9: one round and its re-check.** After the fix, `goal gate --final` runs again, and the **same** quality-engineer and security-engineer re-check through their conversations. Each finding is `closed` or `open`, plus what the fix broke. This is the checkpoint's re-check, not a new hunt.
  - A new finding the fix did not cause goes to `open.md` and the `<area>-hardening` goal, never a round.
  - A second round, with new agents, runs only for what the re-check left open.
  - A `should` left open after the re-check follows the risk policy.
  - A round and its re-check spend one round of the budget. Fable still comes in from the third round.
- **Step 8: a checkpoint's review is not redone.** Every criterion is judged on the whole goal. The code is reviewed only where no checkpoint looked: the diff since the last checkpoint and the seams between tickets. The security-engineer also gets the tickets whose new `Checked by:` line (written at step 7 (e)) lacks it. A goal with no checkpoint is still reviewed on `<baseline>...HEAD`.
- **Step 3, `to-goal` and the quality-engineer: a checker closes.** A criterion about a new script or checker lists the classes of input it refuses. A class outside the list is a hardening item (a `nit` marked `hardening`), never a reproval. "Refuse anything else" never closes, because it means equalling the runner's parser.
- **security-engineer card.** It gains the re-check paragraph the quality-engineer already had.
- **Word budget.** The command grew by 108 words and the command plus the cards by 221, stated in `tests/lean.test.mjs`.

## [0.41.0] - 2026-11-15

**One gate per moment, the walk of a goal read from the disk, and a verification that does not repeat a green proof.** These are M2, M3 and M6 of the graph-engineering analysis, in one release at the founder's choice ("Sim, junta os três"): all three work on steps 7 to 9 and `goal.mjs`, and all three cut what the Engineer and the final verification spend.

Measured on the pilot project:
- the Engineer typed five to eight commands per checkpoint and per round, and was 19 to 64% of a goal's tokens;
- its e2e and perf went red beside the verifiers' builds and were green alone (issue 89);
- the raw log it committed as evidence held 42 refresh tokens from the e2e request log (issue 105);
- where a goal stood was inferred from prose after every wake-up.

### Added
- **`npm run goal -- gate <slug> --ticket <NN> --since <sha>`**, the checkpoint gate of step 7 (a). It runs, one after the other:
  - `check-boundaries`, when the project has it;
  - the build and the affected tests (`turbo --filter=...[<sha>]`);
  - the ticket's proof;
  - `format:check`, when the project has it;
  - the size against the baseline that `baseline.md` records.

  Exit 1 is red. Exit 3 is green with the size budget blown: deliver in parts.
- **`npm run goal -- gate <slug> --final [--base <sha>]`**, the deterministic layer of step 8. It runs the build, `npm test`, `goal check`, the contract's proofs, the backend e2e and `perf --changed <baseline>`, one after the other, each sensitive one in a database of its own when the project has `db:scratch`. The p95 reports and never blocks: a red perf is exit 3, with a line saying to read it for a non-2xx.

  Both modes:
  - stop at the first red, and print the steps after it as `not run`;
  - print one `R <step> exit <n> <seconds>` line per step;
  - write the raw output to the system temp folder, outside the repository.

  The evidence is the `R` lines.
- **`npm run goal -- next <slug> [--json]`**, where the goal is and the next action, read from the disk. It runs nothing. It covers:
  - the contract to write (step 3) and the founder's gate 2 (step 4);
  - the branch and baseline (step 5, including a red baseline) and the plan (step 6);
  - a checkpoint per `built` ticket (naming the security-engineer for a `trust` ticket), an `open` ticket to carry or fix, and the next ticket of the frontier with two lanes when the graph allows (step 7);
  - the final gate (step 8);
  - the next round, with `Class:` on a second failure and Fable from round 3 or a third reproval (step 9);
  - a spent budget, which goes to the risk policy;

### Changed

- The `platform-engineer`'s "Branch and baseline" mission became "Tooling that differs": it only comes in when the script exits 4, to read the two versions of the script the project changed.
- The `full-stack-developer` does not diagnose the Playwright browser that does not open on Windows (`spawn UNKNOWN`, Code Integrity refuses the executable): it runs the suite in a Linux container. In `ci-time-20` this cost 17 minutes.

## [0.31.0] - 2026-11-13

**CI runs by moment, and p95 reports during development.** Measured on the pilot project on 2026-11-13: the PR run took ~21 min (Playwright 609 s, perf 165 s, backend e2e 157 s); three runs went red on `/agent/chat`, and in the same run, same code and same machine the route measured 1362 ms and then 625 ms. A p95 from a shared runner does not say the change made the route slow, and each red cost a round of the goal. With the new design on the pilot project: push to the PR in 3 min 11 s, ready PR in 6 min 20 s, full nightly run in 22 min.

### Changed
- **Generated `ci.yml`, by moment.** Every push to a PR, draft or not: title, scanners, contract, build, `npm test`. Ready PR (`ready_for_review` was added to the triggers): plus the backend e2e and the Playwright smoke, which is the merge gate. Every night on main (daily cron; only the scanners if nothing landed in 26 h) and on `workflow_dispatch`: everything, the whole Playwright suite and the p95 of each route, which **reports** (a warning and a line in the run summary) and never fails the run. `workflow_dispatch` with `stage: pre-release`: everything, and the p95 **fails** the run. No test leaves CI: it changes moment.
- **Playwright smoke.** The scope step chooses what a ready PR runs: the specs in `apps/frontend/e2e/smoke.txt` plus every spec the PR wrote; the whole suite when the PR touches the harness (config, helper, fixture). A name outside `e2e/<name>.spec.ts` or a file that does not exist fails the step, with the name: the smoke never shrinks because of a typo. The `platform-engineer` card states the criterion for the list and that the names go to `npx playwright test` without `--` (with it Playwright ignores the filter and runs the whole suite, as in a pilot-project run).
- **Step 8 of `/engineer`.** The p95 reports and does not block the goal: the table goes into the evidence as `reported`; a route over budget and perf that exits 3 become roadmap items, never a round, and nothing goes back to the `full-stack-developer` because of them. Still blocking: a non-2xx response, `expectQueryBudget` in the e2e, and a contract criterion that is a latency target.
- **Step 10 and the Release mission.** The goal's PR opens ready, never as a draft. Before `npm run release`, the `platform-engineer` runs `gh workflow run ci.yml --ref main -f stage=pre-release` and only releases with it green.
- **Rule 11** of `ARCHITECTURE.md`: the query budget blocks every ready PR; the p95 runs every night, reporting, and blocks the `pre-release` run. The `quality-engineer` does not flag a p95 over budget: the finding is a route with no number.
- A red nightly run on main is a fix before any goal (it used to be the weekly run).

### Added
- `tests/ci-moments.test.mjs`: runs in bash the scope step (smoke plus the PR's specs, whole suite on the harness, wrong name refused) and the Latency Budget step (exit 1 and 3 report in the nightly; only `pre-release` fails), and reads the rules in the command and in the cards.

### What was not proved
- The red path of the Latency Budget was exercised in bash, not in a real run: the pilot project's runs that day stayed within budget.
- An existing project does not get the new `ci.yml` through `tooling-sync`: the pilot project got it; another project needs a `platform-engineer` mission.
- The squad's word budget went up by 141 words (the command went down by 4): the new text is the CI-by-moment recipe in the `platform-engineer` card.

## [0.27.0] - 2026-11-13

The latency budget asks the base before blocking. Measured on the pilot project: of the 15 red CI runs since November 1, 4 were in the latency step, and the last 3 PR failures were all in it. In none of the 4 was the cause the PR's code: twice the runner was slow (25% slower on untouched routes; `/health` from 1.8 to 5.6 ms), once the test's scripted model was storing every call, and once the 20 connections were the same person, queued on a per-person lock. Each red became a diagnosis mission (10.3M, 7.4M and 3.7M tokens), new CI runs and two founder decisions. The gate asked "does this route respond under N ms on this machine?", and the answer changes with the machine.

### Added
- **`perf` compares with the base.** A route over budget in two measurements, with all responses correct, and that the base already had, is also measured on the base's code, on the same machine and in the same run: the script checks out the base (the `--changed` ref) in a worktree, runs `npm ci` and the build, and measures the same routes twice in a database of its own (`db:scratch`). More than 1.25 times slower than the base (`regressionRatio` in `perf.config.json`, best p95 on each side): exit 1, with both numbers. Not slower: exit 0, one `not this change` line per route and a warning on the PR run. A new route, a run without `--changed` and a base that does not build or does not respond: the budget decides, as before. `PERF_BASE_URL` measures a base that is already up; `PERF_COMPARE=0` turns it off.
- **One person per connection.** The perf setup can return `actors`, and each connection measures as a different person. Twenty connections as one person measure that person's lock, not the route.
- `tests/perf-base.test.mjs`, seven tests that run the script against two servers, and the smoke step `perf-compares-base`, which builds the base of a generated project and requires a red only from the change that made the route slow.

### Changed
- **Rule 11** (`ARCHITECTURE.md`): a p95 over budget fails the change when the route is new or when it became slower than the base measured on the same machine. An existing project does not have the rule rewritten by `tooling-sync`: changing the text is an ADR of the project.
- **`/engineer`, final verification:** the `not this change` line becomes a roadmap item, never a round, and a red perf only goes to the `full-stack-developer` with both measurements. The command came to 7,569 words, and the command and the cards together went from 18,739 to 18,738; the new text was paid for with the history of the old CI recipe in the `platform-engineer` card and two step 8 explanations the scripts already give.

## [0.22.0] - 2026-11-11

Lean code in a goal-driven squad, from reading [ponytail](https://github.com/DietrichGebert/ponytail) by Dietrich Gebert (MIT). There the agent guesses what nobody asked for; here the contract decides: it is the code that no criterion, limit or rule requires.

### Added
- **Architecture rule 15: nothing exists that the goal does not ask for.** Before creating, what already exists, in this order: the project, `@<ns>/shared`, the platform, an installed dependency. No abstraction, option or code "for later" beyond what the rules ask; scaffolding no criterion exercises is removed before the commit.
