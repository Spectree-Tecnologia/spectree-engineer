# Missão CI

<!-- moved verbatim from agents/platform-engineer.md:22-22 (0.31.0) -->

**CI.** Minuto de Actions é orçamento: repositório privado paga por minuto de job, e o plano Free da organização inclui perto de 2 000 minutos Linux por mês, somados entre todos os repositórios privados dela. Por isso a receita é uma só: **um workflow, um job, nunca em push**. O `config-project` grava `.github/workflows/ci.yml` assim, e você o estende sem mudar a forma. **O que roda depende do momento:** todo push num PR roda título, scanners, contrato, build e `npm test`; PR pronto (não draft) soma o e2e do backend e o smoke do Playwright, e é o gate do merge; a main roda tudo toda noite (só os scanners se nada entrou em 26 h) e no `workflow_dispatch`, com o p95 **reportando**; `stage: pre-release` faz o p95 **falhar** o run, o gate antes do deploy. Teste nenhum sai do CI: muda de momento. O que o job faz, em ordem: título do PR em Conventional Commits, lido da API (falha em segundos, antes de instalar; o squash merge leva esse título para a main); gitleaks na história; `npm audit --audit-level=high` e osv-scanner só quando o PR toca `package-lock.json`; squawk nas migrations que o PR adiciona (migration apagada falha, com o nome); e, quando o diff não é só documentação (`*.md`, `docs/`, `.scratch/`): `npm ci`, Postgres pelo `docker-compose.yml` do backend com o `.env.example`, `npm run build`, `migrate deploy`, `db:roles`, seed, `npm test`, o e2e do backend (só em PR pronto) e as provas `in ci:` do contrato; no run inteiro da main, `npm run perf` em todas as rotas (no banco em que ninguém escreveu, nada mais rodando no runner) e os scanners do lockfile sem condição. **Nada roda em push.** O run do PR prova o commit de merge com a main daquele momento, e é por isso que só se mergeia branch que contém a ponta da main (missão PR e merge). O que você nunca faz nesse arquivo: segundo job, matrix ou shard (velocidade de relógio que se paga em minutos); gatilho `push:`, `types: [edited]` ou `pull_request_target`; `timeout-minutes` acima de 20 (job travado é cobrado até o teto); workflow novo para o que cabe num passo; `${{ }}` dentro de `run:` (`github.base_ref`, título e nomes de arquivo chegam por `env:`), `head_ref`, permissão além de `contents: read` e `pull-requests: read`, checkout sem `persist-credentials: false`. Passo próprio do projeto (`format:check`, `lint`) entra antes do build, com o mesmo `if` de código. **Playwright** (`playwright.config.*`) entra como passos no fim do mesmo job, em estado zerado: `docker compose down -v && docker compose up -d --wait postgres` em `apps/backend` (banco novo, mesmas URLs), `migrate deploy`, `db:roles`, seed, backend iniciado com os limites elevados por env **só os que a suíte não afirma** (rate limit de login, throttler; um limite que um spec testa, como o de páginas por dia, fica no valor real), saída em `tee backend.log`, frontend buildado contra ele (`NEXT_PUBLIC_API_URL` no `env:` do passo de build) e iniciado com `tee frontend.log`, `PLAYWRIGHT_BASE_URL`, `BACKEND_LOG` e `FRONTEND_LOG` no env, browsers em cache (`actions/cache` em `~/.cache/ms-playwright`, chave pela versão do Playwright no lockfile; cache acertado, só `npx playwright install-deps chromium`), `forbidOnly: !!process.env.CI` no `playwright.config` (um `test.only` esquecido falha em vez de pular a suíte), logs enviados como artifact só em `failure()` com `retention-days` curto (carregam link mágico); cada passo com `github.event.pull_request.draft != true` no `if:`, e o último roda `SPECS` (`steps.scope.outputs.playwright`): `full`, ou as specs de `apps/frontend/e2e/smoke.txt` e as que o PR escreveu, passadas **sem `--` antes dos nomes** (com ele o Playwright roda a suíte inteira); o `smoke.txt` é seu: uma spec por jornada que todos percorrem, stack real, menos de ~3 min somados, o porquê num comentário `#`; o helper de login da suíte lê a credencial de teste (link mágico, código) de uma rota só de teste ou do log, nunca da UI de e-mail, e um limite em memória (tentativas por e-mail por dia) só é confiável porque o backend acabou de subir. **Dependabot:** o `dependabot.yml` do scaffold abre um PR agrupado por mês por ecossistema (cada PR é um run); correção de segurança não espera o mês, então ligue uma vez `gh api -X PUT repos/<owner>/<repo>/vulnerability-alerts` e `gh api -X PUT repos/<owner>/<repo>/automated-security-fixes` (grátis em repositório privado). **gitleaks e o squash merge:** a fingerprint em `.gitleaksignore` leva o sha do commit, e o squash descarta os shas da branch; fingerprint de commit da branch passa no PR e falha no run noturno da main para sempre. Só fingerprint de commit que já está na main; linha tocada na branch leva `gitleaks:allow` inline; valor de exemplo que a história pode reintroduzir sem o marcador vai para `.gitleaks.toml` (`[extend] useDefault = true` + allowlist com `condition = "AND"`, o path e o valor exato). A prova do PR inclui um scan da branch squashada (`git clone --no-local`, `git merge --squash`, gitleaks nele). **Prova local do gitleaks:** pelo `npm run check:pr`, que monta o volume certo no Windows e recusa `0 commits scanned`. As imagens do `ci.yml` estão pinadas por tag e digest e o `squawk-cli` por versão exata: o Dependabot não as acompanha, o bump é seu, na vigilância de stack, e o `check-pr.mjs` lê os mesmos pins do arquivo. Vulnerabilidade que o osv-scanner acusa e o `npm audit` não: corrija pelo bump; sem versão corrigida, `osv-scanner.toml` ao lado do lockfile com `[[IgnoredVulns]]`, `id` e `reason`, mais uma linha em `decisions.md`; nunca o passo desligado. Aviso do squawk numa migration: `NOT NULL` sem default, índice sem `CONCURRENTLY` ou rename em tabela com dado é gate 3, o resto se corrige na migration antes do merge.
