# Objetivo, passos 10 a 12 (seção 3)

10. **PR e merge.** Chame o Skill tool com `pr`: o corpo do PR é o objetivo e a tabela de critérios com a evidência. O **platform-engineer** roda `npm run check:pr` na branch do objetivo (o que o CI só roda no PR, e o contrato pronto: aprovado, todo critério `met` ou dispensado por emenda; FAIL vira correção antes de abrir), abre o PR e espera o CI. **Um PR por objetivo, um push, um run:** minuto de Actions é orçamento, e a prova que decide já rodou aqui. O PR abre pronto, nunca em draft: o run de PR pronto é o gate do merge. CI verde → ele mergeia na main e apaga a branch, **sem perguntar**. Contrato com prova que espera: a `in ci:` se decide pelo run verde do PR, com o id dele na evidência; a `after merge:` roda na main mergeada (`npm run goal -- prove <slug> --after-merge`, pelo platform-engineer), e até ela sair 0 o contrato é `Status: landed on <data>`, não `met`. Prova vermelha depois do merge é correção antes de qualquer outro objetivo, pelo fluxo de Bug. CI vermelho → um full-stack-developer novo reproduz local, corrige, e a correção sobe num push só (gasta uma rodada do orçamento). Deploy e exposição pública continuam gate 1/3; aberto o gate 1, a missão Release do **platform-engineer** (`npm run release`, `/ready` verde, rollback = imagem anterior) é quem sobe.
11. **Retro.** Chame o Skill tool com `retro` nesta mesma sessão, antes de limpar contexto. Cada candidato tem um destino: o que é do **projeto** (navegação, check faltando, regra de review, `CODING_STANDARDS.md`) você aplica na hora quando cabe numa linha, ou vira item do `docs/roadmap.md`; o que é do **plugin** — um agente que leu errado a missão, uma skill de monólito que gerou arquivo quebrado, um script, um template, um passo deste comando — não se conserta no projeto: abra uma issue, sem perguntar, com `gh issue create --repo Spectree-Tecnologia/spectree-engineer --label enhancement` (`bug` quando algo gerado não compila ou não passa), título em uma frase e corpo com o que aconteceu, `arquivo:linha` no plugin, o projeto e a mudança onde apareceu, e a correção proposta. Sem `gh` autenticado, grave o mesmo texto em `.scratch/plugin-issues.md` e relate. Objetivo que acrescentou ou mudou componente do design system: despache o **ui-ux-designer** para republicar o artefato do design system, com o critério de saída "os arquivos publicados são os de `docs/design/design-system/project/`", senão o próximo objetivo prototipa sobre um kit que não existe. Grave no contrato, logo abaixo do `Status`, a linha `Landed: PR #<n>, <linhas> product lines, CI <min> min` (o `npm run goal -- size` e a duração do run, do relato do platform-engineer), `Status: met on <data>`, e marque o item no `docs/roadmap.md`. Rode `npm run goal -- spent <slug> --write` (`--session <id>` se o objetivo não rodou numa sessão de item): grava no contrato a linha `Spent:` (relógio, horas no limite de uso do plano, horas esperando o fundador, tokens, turnos) e imprime os tokens por papel. `npm run goal -- stats` mostra o conjunto dos objetivos: número que piora de um para o outro é candidato a regra. O que a verificação reprovou mais de uma vez no como do full-stack-developer é candidato a regra em `docs/architecture.md`: o que estava só na cabeça do squad passa a ser lido pelo próximo full-stack-developer.
12. **Próximo.** Relate em uma linha o que foi mergeado. Sessão de item: encerre aqui; a principal abre o próximo (seção 7). Sessão principal construindo sem a ferramenta: comece o próximo item do roadmap. Roadmap vazio: diga isso e pergunte o que vem.

O que nunca muda: os quatro gates; o gate de arquitetura antes do código e o pipeline de qualidade e segurança antes do PR; as regras de `docs/architecture.md` (o como é livre **dentro** delas, e `check-boundaries` é o juiz); prova por exit code; "nada fica rodando"; um PR, um push, um run.
